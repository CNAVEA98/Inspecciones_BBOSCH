## Cómo registrar una mejora

1. Agregue una entrada **al inicio** de la sección «Registro» (la más reciente arriba), con este formato:

   ```
   ### AAAA-MM-DD · Título corto
   - **Autor:** nombre
   - **Versión:** V1.1.x (la nueva, ver «Versiones» abajo)
   - **Qué se hizo:** 1 a 3 líneas
   - **Archivos:** rutas principales
   - **Verificación:** comando y resultado real (lint, tsc, tests, build, prueba manual) o «no verificado» y por qué
   - **Pendiente / riesgos:** lo que quedó sin hacer o sin probar
   ```
2. Actualice la sección «Estado actual» y la lista «Pendientes» si cambian.
3. Si un cambio modifica una decisión, anótelo también en «Decisiones».
4. No borre entradas antiguas: si algo se revierte, agregue una entrada nueva que lo diga.

## Al iniciar cada sesión (obligatorio)

Cada vez que se abre una sesión nueva (persona o Claude), **antes de cualquier cambio**, compare el repositorio de
GitHub con la copia local y baje lo último:

1. `git fetch origin` y `git status`: diga en qué rama está y si hay cambios locales sin commit.
2. Compare con GitHub: `git log --oneline HEAD..origin/main` (lo que falta bajar) y `git log --oneline origin/main..HEAD`
   (lo local que GitHub no tiene). Revise también las ramas remotas nuevas (`git branch -r`) y los PR abiertos.
3. Si `main` está atrasado: `git switch main` y `git pull --ff-only origin main`. Si está en una rama de trabajo, traiga
   `main` a esa rama (`git merge origin/main`) y resuelva conflictos conservando ambas entradas de la bitácora.
4. Si hubo cambios, vuelva a leer esta bitácora (Registro, Estado actual y Pendientes) y, si cambiaron dependencias o
   migraciones, corra `corepack pnpm install` y `corepack pnpm supabase db reset`.
5. Si el `pull` falla (credenciales, conflicto, rama divergente), no lo fuerce: anote el error y avise antes de seguir.

## Decisiones

- **Sin señal: se migra a React Native (2026-11-06, decisión de Cristóbal):** la PWA se abre desde un enlace y no cumple el trabajo sin señal en terreno; por eso la prueba de aceptación sin señal (pendientes 9 y 21) se hace en la app nativa y no se invierte más en el modo sin red de la PWA.
- **Contraseñas de las cuentas de prueba (2026-11-06):** salieron del repositorio (V1.1.3) pero siguen en el historial público y vigentes en el remoto; Cristóbal decidió no rotarlas ni volver privado el repo por ahora. Rotarlas antes de usar datos reales.
- **Repositorio público (2026-11-06):** se mantiene público porque Cristóbal y Manuel trabajan con cuentas distintas. Un repositorio privado también admite colaboradores; el riesgo es que queden expuestos `supabase/seed_usuarios_dev.sql` y lo que la bitácora cita del proyecto remoto. Revisar el historial de git antes de cualquier cambio.

- **Seguimiento de hallazgos (2026-10-31, pedido por MLP):** a la OT padre se le carga la inspección firmada (la evidencia de lo detectado); si hay hallazgo, el supervisor crea un aviso subsecuente en SAP, al que se carga aparte un informe de mejora de la condición (**fuera de la app, no se integra**). Por eso el seguimiento **no bloquea las firmas** ni toca `review_inspection`. Gatillo: el alcance (lo de Bbosch 23 kV lleva aviso; lo que requiere apoyo de terceros se canaliza con MLP), no la severidad, que solo sugiere la prioridad. Solo cuentan los hallazgos «Malo». El seguimiento va en la tabla `finding_followups` porque los hallazgos son inmutables tras el envío; solo lo escribe el RPC `set_finding_followup` (supervisor y administrador; el programador lee). Se dice «dar aviso a Supervisión», no «Torre de Control».
- **El técnico descarga el PDF de sus inspecciones (2026-10-31):** se reutiliza el generador de los otros roles y la lectura pasa por RLS con su sesión, así que solo obtiene las suyas. Para mostrar quién firmó se le permite leer el perfil de los firmantes de **sus** inspecciones (`0013`). El service worker no intercepta las rutas `/pdf`.
- **PDF sin tablas partidas (2026-10-31):** cada grupo de ítems se mantiene entero en una página (si no cabe, pasa completo a la siguiente) salvo que por sí solo supere una página; es una estimación de altura, no una medición.
- **No instalar «Free Claude Code» en este equipo (2026-10-31):** es un proxy de terceros que reenvía código y prompts a proveedores gratuitos; el equipo parece corporativo y el repositorio es infraestructura de MLP. Se hizo un intento de instalación que falló en el primer paso (`uv.exe` en uso) y solo dejó la carpeta `.fcc/logs` en el perfil del usuario (borrable). No se reintenta sin revisión previa de TI.
- **Skills del proyecto (2026-10-31):** `react-best-practices` y `web-design-guidelines` quedaron en `.claude/skills/` (auditoría en `docs/AUDITORIA_REACT_UI_TECNICO.md`); no reemplazan a `docs/DESIGN.md` ni a `AGENTS.md`.
- **Despliegue de prueba (2026-10-30):** Vercel (`inspecciones-bbosch`, repositorio `CNAVEA98/Inspecciones_BBOSCH`, producción = rama `main`) + Supabase creado desde la integración de Vercel (organización «CNV», región São Paulo, plan Free). La integración carga en Vercel `NEXT_PUBLIC_SUPABASE_URL` y `NEXT_PUBLIC_SUPABASE_ANON_KEY` (las que usa la app) y otras variables (`SUPABASE_SERVICE_ROLE_KEY`, `POSTGRES_*`…) que la app **no** usa; nunca deben llevar prefijo `NEXT_PUBLIC_`. Sin ramas de base de datos para Preview. El esquema remoto se aplicó pegando un SQL único (migraciones 0001–0011 + `seed_catalogo.sql`, dentro de una transacción); no se ejecutó `seed_usuarios_dev.sql` en remoto.
- **Cuentas genéricas por usuario, sin correo (2026-10-30):** no se crean cuentas por persona (la gente olvida contraseñas). Hay 7 cuentas compartidas que se ingresan con **usuario**: `ADMINISTRADOR`, `SUPERVISOR_A`, `SUPERVISOR_B`, `PROGRAMADOR_A`, `PROGRAMADOR_B`, `TECNICO_A`, `TECNICO_B` (no distingue mayúsculas). Supabase Auth exige correo, así que se usa uno interno `usuario@mlp.local` que nunca se muestra y no parece un correo real. El rol «planificador» se muestra como «Programador» (la ruta y el código siguen en `planner`/`/planificador`). La trazabilidad por persona la da el campo «quién realizó la inspección». Las contraseñas del seed son de prueba: **hay que cambiarlas antes de producción**.
- **Formatos en código, TAG desde el Maestro (2026-10-30; la parte de «formatos en código» quedó reemplazada el 2026-11-03 por la tabla `formatos`, ver «Catálogo de formatos en la base»):** el catálogo de 60 formatos vive en `src/lib/formatos/catalogo.ts` (fuente única; habilitar uno = cambiar su estado y cargar su plantilla). Valle es una quinta área. Los TAG vienen de `src/data/maestro-tags.json`, generado con `scripts/export-maestro.py` (Python + openpyxl solo para el script). Los TAG provisionales (propuesto/reasignado) se pueden elegir y se marcan en el registro para revisión; no se bloquea al técnico por no tener el TAG oficial.
- **Cuentas creadas por el equipo, no por la app (2026-10-30):** no habrá pantalla de alta de usuarios; las cuentas las genera el equipo de desarrollo para que solo las use personal de la empresa. No hay autoregistro.
- **PWA con `@serwist/turbopack` (2026-10-30):** no se usa `@serwist/next` porque exige webpack y con webpack el CSS de Tailwind no se genera (el loader es solo de Turbopack). El service worker se sirve desde una ruta (`/serwist/sw.js`) y solo se registra en producción. Solo el área del técnico funciona sin red.
- **Roles y firma doble (2026-10-30):** admin, supervisor, planificador y técnico, cada uno con turno A/B (el admin sin turno). El turno es solo etiqueta. Firma en dos etapas: supervisor y luego planificador. Solo el admin cambia rol y turno. Cuentas nuevas parten como técnico y no hay autoregistro.
- **Diseño «Cobre»** (grafito + cobre, bordes redondeados, números tipo instrumento), aprobado por el usuario. Nació de la familia SAP de awesome-design-md; IBM Carbon descartado. Detalle en `docs/DESIGN.md`.
- **Sin geo-referencia:** se evaluó y el usuario la descartó; no hay columnas geo en el esquema.
- **Sin modo oscuro, analytics ni notificaciones push** (fuera de alcance).
- **Next 16:** el antiguo middleware se llama `src/proxy.ts`. Se desactivó `cacheComponents` (venía activo desde create-next-app) porque la app es autenticada y dinámica.
- **Rol:** el registro crea siempre `technician`; solo un supervisor lo cambia (acción de servidor + RLS + trigger `guard_profile_role`). Un supervisor no puede quitarse su propio rol.
- **Plantillas versionadas e inmutables** una vez publicadas; la inspección guarda `template_id` y `template_version`.
- **Folio** `INS-AAAA-NNNNNN` lo asigna el servidor al enviar. Los IDs de inspección, fotos y hallazgos se generan en el cliente (idempotencia offline).
- **Fotos** comprimidas en el cliente (lado mayor 1600 px, JPEG 0,7), ruta `{uid}/{inspection_id}/{foto}.jpg` en bucket privado.
- **ML exige observación; NR exige motivo; la foto es opcional en todos los estados** (validado en cliente y en el validador de plantillas). Hasta el 2026-10-30 ML exigía también foto; se cambió a pedido del usuario para todas las inspecciones.
- **Firmas (2026-10-31): solo firman el encargado de la actividad, el supervisor y el planificador; los participantes se anotan pero no firman** (campo de texto opcional, clave `_lista_participantes`). El encargado firma al enviar, en el cierre del formulario, junto con su nombre (rol «Encargado de la actividad»); se guarda como adjunto `participant_signature` y la respuesta `_participantes`, nombres heredados que se mantienen para no cambiar el esquema ni los registros existentes (hoy significan «encargado»). La firma del supervisor y del planificador va en la tabla `signatures`. Los firmantes se llaman siempre «Supervisor Bbosch» y «Planificador Bbosch».
- **Fuente Geist** vía `next/font` (se descarga en el build; requiere internet al compilar).

- **Versiones (2026-11-03):** la app parte en V1.1.0 y cada mejora unida a `main` sube el último número; la versión se ve al pie de cada pantalla y se anota en la bitácora (ver «Versiones»).
- **Privacidad (2026-11-03):** aviso informativo con «Entendido», no consentimiento (base: relación laboral/contractual y contrato Bbosch–MLP). Sin banner de cookies mientras solo haya cookies necesarias; si algún día se agrega analítica, hará falta banner y consentimiento. Fotos siempre sin metadatos.
- **Migraciones remotas antes de unir (2026-11-03):** un PR que necesita migraciones nuevas solo se une a `main` **después** de aplicarlas en el Supabase remoto y verificarlas, porque Vercel despliega `main` de inmediato. Se aprendió con el PR #9 (catálogo vacío para el técnico hasta aplicar 0015–0019).
- **Gestión de formatos (2026-11-03):** supervisor y administrador editan, crean, activan y desactivan formatos; el planificador solo consulta. Un formato nuevo nace desactivado.
- **Catálogo de formatos en la base (2026-11-03):** la fuente de los formatos es la tabla `formatos` (antes `catalogo.ts`). Un formato con historial nunca se borra: se desactiva (`activo = false`). La plantilla se enlaza por códigos de tipo de equipo y modo, no por id, para que la migración no dependa del seed.
- **Edición de formatos (2026-11-03):** editar un formato nunca modifica una versión publicada: se inserta la siguiente. Escriben supervisor y administrador; el planificador consulta. Quitar un ítem en una versión nueva es seguro porque cada inspección conserva su `template_id`; por eso no hizo falta «ocultar» ítems. El `id` de un ítem existente es de solo lectura.

## Cómo correr el proyecto

```bash
corepack pnpm install
corepack pnpm lint
corepack pnpm tsc --noEmit
corepack pnpm test
corepack pnpm build
corepack pnpm dev            # necesita .env.local (copiar de .env.example)
```

Con Docker funcionando: `corepack pnpm supabase start` y `corepack pnpm supabase db reset` (`db reset` **borra** los datos locales y recarga `seed_catalogo.sql` y `seed_usuarios_dev.sql`).
Pruebas de la base: `corepack pnpm supabase test db`. Para el `.env.local` local, los valores salen de `corepack pnpm supabase status`.
Para regenerar la lista de TAG: `python scripts/export-maestro.py` (ver `docs/EXPORT_MAESTRO.md`). Para probar en línea: `docs/DEPLOY_VERCEL.md`.
Referencia visual interactiva (sin servidor): `docs/muestras/formulario-transformador-piso.html`.
